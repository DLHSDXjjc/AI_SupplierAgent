# 供应链自动补货Agent — 面试问答手册

> 基于本项目的实际实现整理，所有回答均与代码一致，可溯源。

---

## 问题1：你这个Agent的整体架构是什么样的？

用户提问 → Streamlit前端 → HTTP请求 → FastAPI /ask接口 → SupplyChainAgent.chat() → AgentExecutor执行ReAct循环 → LLM自主决策调工具 → 返回结果

```
用户输入: "SKU001库存够不够？"
    │
    ▼
Streamlit前端（纯展示，调FastAPI的HTTP接口）
    │
    ▼
FastAPI后端
  agent = SupplyChainAgent()  ← 服务启动时创建一次
  agent.chat(query)           ← 每次请求调用
    │
    ▼
AgentExecutor（LangChain框架，不是我写的）
  ReAct循环：Thought → Action → Observation → ... → Final Answer
    │
    ├── 第1轮：LLM匹配docstring → 选inventory_query → 查CSV → 库存50/安全库存200
    ├── 第2轮：LLM继续推理 → 选reorder_calculator → EOQ计算 → 建议补货844件
    └── 第3轮：LLM判断信息足够 → Final Answer
    │
    ▼
提取3样东西返回前端：
  1. answer（最终回答）
  2. tools_used（["inventory_query","reorder_calculator"]）
  3. sources（["补货策略"]）
```

**哪些是我写的，哪些是框架做的：**

| 环节 | 谁做的 | 具体内容 |
|------|--------|----------|
| System Prompt | 我写的 | Agent人设、工作原则、流程 |
| @tool函数（8个） | 我写的 | 知识检索、库存查询、补货计算、下单等 |
| docstring工具描述 | 我写的 | LLM靠这个判断调哪个工具 |
| LLM选工具+推理 | LLM自己做的 | 读docstring，语义匹配，决定调什么 |
| 解析LLM输出 | LangChain框架做的 | 解析Thought/Action/Action Input |
| 调用@tool函数 | LangChain框架做的 | 框架调，不是LLM直接调 |
| 循环推理 | LangChain框架做的 | AgentExecutor的while循环 |
| 错误纠正 | 我写的 | _handle_parsing_error给简洁提示 |

核心：**我写工具和Prompt，框架负责调度，LLM负责决策。**

## 问题2：为什么选LangChain？对比过其他框架吗？

3个原因：

1. **Agent生态最成熟。** LangChain的ReAct Agent、工具调用、AgentExecutor是现成的，注册@tool函数就能用。LlamaIndex更偏RAG检索，Agent能力弱；Dify是低代码平台，灵活度不够，做定制化工具调用链路不好控制。

2. **和现有技术栈契合。** 后端主系统是Java，Agent作为旁路Python服务，通过FastAPI暴露RESTful接口，注册到Nacos给Java网关调用。LangChain是Python生态，和FastAPI天然配合。Dify部署方式不好和现有微服务架构融合。

3. **工具调用最灵活。** Agent需要4种不同类型工具——语义检索、精确查询、数学计算、模拟写入，每种数据源和调用方式不同。LangChain的@tool装饰器很灵活，docstring就是工具描述，LLM自动匹配。

## 问题3：RAG这部分，文档向量化具体怎么做的？

**Embedding模型：moka-ai/m3e-base**，中文优化，768维。没用OpenAI的text-embedding-ada-002，因为文档全是中文，m3e-base中文语义匹配更好，且可本地部署，不依赖外部API。

**分块：RecursiveCharacterTextSplitter**，按字符数切，不是固定token数。chunk_size=300，chunk_overlap=40。

**为什么选300？** 供应链管理文档一个完整策略要点大概200-400字，300字刚好覆盖一个完整要点。500字会混入不相关策略，100字会把策略切成碎片。

**overlap=40：** 中文一个句子大概20-50字，40字overlap保证跨段落信息完整，不会在公式中间切断。

**切分逻辑不是硬切：** 按分隔符优先级递归切——\n\n（段落）→ \n → 。→ ；→ ，→ 空格 → 硬切。300是上限，实际大多数分块不到300字。

**三个文档分开存：** 避免不同主题内容被揉进同一段，元数据可标注来源，维护方便。

## 问题4：ChromaDB是本地还是云端？数据量多大？Top-K设多少？

**本地部署**，PersistentClient存磁盘，重启不丢。

**数据量：3个文档，24个分块**（补货策略6段、库存管理政策8段、供应商管理指南10段），不到1MB。

**Top-K默认3。** 原因：
1. 文档按主题分，结构清晰，Top-3能覆盖相关信息
2. Top-K越大LLM上下文越长，不相关内容会干扰回答

**相似度阈值0.5。** `1/(1+L2距离)` 低于0.5直接过滤。

如果数据量上百万级，考虑换成Milvus或Qdrant。当前24条，ChromaDB够用。

## 问题5：ReAct Agent的流程怎么走？工具调用失败怎么办？

**8个工具**：knowledge_search、inventory_query、inventory_alert、supplier_query、reorder_calculator、place_order、query_order、list_orders

**流程**：Thought → Action → Observation循环。LLM读docstring匹配工具，框架解析输出执行调用，结果喂回LLM，直到Final Answer。最多20轮。

**工具调用失败两种情况：**

1. **格式解析失败**（LLM输出格式不对）：调用 `_handle_parsing_error` 返回简洁纠正提示，LLM重新生成，不会直接报错。

2. **工具执行失败**（查不到数据）：工具内部返回友好文本（如"未找到SKU编号XXX"），LLM读到后换方式回答，不会崩溃。

**当前没有降级机制。** 如果inventory_query真的超时，Agent直接报错。可以优化为：工具失败时自动调knowledge_search给参考性回答。

## 问题6：Agent怎么决定先调哪个工具？是LLM自己决定还是固定顺序？

**LLM自己决定，不是固定顺序。** 没有写if-else规则链。

LLM读每个@tool的docstring描述，和用户问题做语义匹配：
- "SKU001库存多少" → 匹配inventory_query
- "安全库存怎么算" → 匹配knowledge_search
- "补多少货" → 匹配reorder_calculator

**System Prompt里写了工作流程作为引导**（查询库存→评估紧迫度→计算补货量→...），但这是参考路线图，不是红绿灯，LLM会根据问题灵活调整。

| | LLM自主决策（我们用的） | 固定规则链 |
|---|---|---|
| 灵活性 | ✅ 不同问题不同路径 | ❌ 所有问题走同一条路 |
| 可靠性 | 偶尔选错工具 | 每次都走固定流程 |
| 实现方式 | @tool + docstring | if-else硬编码 |

## 问题7：Agent是多轮对话还是单轮问答？

**当前是单轮问答。** 每次调用 `agent.chat(query)`，不携带之前对话历史。用户下次提问时Agent不记得上一轮内容。

**注意区分两个概念：**
- `agent_scratchpad` = 单次提问内的多轮推理（一次chat内部Thought/Action/Observation循环），每次chat结束后清空
- 多轮对话 = 跨提问的记忆（第2次提问时记得第1次的内容），这个没做

**升级方案：** chat()加history参数拼接历史，FastAPI侧存对话历史，5轮截断防Token超限：

```python
def chat(self, query: str, history: list = None) -> dict:
    if history:
        history_text = ""
        for msg in history:
            role = "用户" if msg["role"] == "user" else "助手"
            history_text += f"{role}: {msg['content']}\n"
        full_input = f"{history_text}用户: {query}"
    else:
        full_input = query
    result = self.agent_executor.invoke({"input": full_input})
```

存储方式：Demo用内存字典，生产用Redis（支持多实例共享+自动过期）。

## 问题8：LLM怎么判断自己的回答够了？

**LLM没有精确判断，是概率推理。** 它根据Prompt模板里的格式要求决定什么时候输出Final Answer：

- 想调工具 → 输出 Thought + Action + Action Input
- 觉得信息够了 → 输出 Thought + Final Answer

LLM根据当前收集到的信息是否覆盖了用户问题的所有部分来决定。比如用户问"SKU001库存够不够"，LLM查到库存50低于安全库存200，又算出补货844件，三个子问题都回答了，就输出Final Answer。

**也会犯错：** 过早终止（没算补货量就回答）或过度调用（反复调工具不终止）。System Prompt写清工作流程可以引导，max_iterations=20兜底防止无限循环。

## 9：补充 — 面试加分回答

**为什么不让LLM直接算补货量，要写成工具？**

因为LLM不会算数，但很会说话。你问它补货量，它自信编一个数字，看着合理但每次不一样。EOQ是确定的数学公式，输入一样输出永远一样。所以计算逻辑写死在工具里，LLM只负责决定"什么时候调这个工具"，工具负责"算出正确结果"。

这也是Agent的核心价值：LLM是决策者不是执行者，算数的事交给工具。Agent = LLM的大脑 + 工具的手脚。

**订货成本和单价不是一回事：**

- 订货成本：每次"下单"这个动作花的钱（采购员工资、沟通、运输、检验），跟数量无关，下一次就是200元
- 单价：每件商品的采购价，买100件就×100

EOQ就是在"下单太频繁（订货成本高）"和"库存压太多（持有成本高）"之间找最省钱的平衡点。

## 10：补货计算的7个公式 — 速查表

### 公式总览（回答什么问题）

| # | 公式 | 回答什么问题 | 一句话 |
|---|------|-------------|--------|
| 1 | **安全库存** | 库存低于多少就要报警？ | 保证不缺货的底线 |
| 2 | **EOQ** | 每次补多少最省钱？ | 平衡"下单太频繁"和"库存压太多" |
| 3 | **提前期需求** | 从下单到到货会消耗多少？ | 下单期间仓库还要出多少货 |
| 4 | **补货点** | 降到多少必须下单？ | 触发补货的警戒线 |
| 5 | **建议补货量** | 这次到底补多少？ | 取"基础需求"和"EOQ"中大的那个 |
| 6 | **紧迫度** | 现在多着急？ | 4档分级：正常/关注/较紧急/紧急 |
| 7 | **可维持天数** | 不补还能撑几天？ | 当前库存÷日均消耗 |

---

### 公式1：安全库存

```
安全库存 = 日均需求 × 提前期 × Z值 × 0.3（波动系数）

Z值对照：
  服务水平90% → Z=1.28
  服务水平95% → Z=1.65（默认）
  服务水平99% → Z=2.33
```

**例子：SKU001 A4复印纸**

```
安全库存 = 30.5 × 7 × 1.65 × 0.3
        = 105.7 → 向上取整 = 106件

含义：在95%服务水平下，至少备106件安全库存来应对需求波动和供应延迟
```

---

### 公式2：EOQ（经济订货量）

```
EOQ = √(2 × 年需求量 × 单次订货成本 / (单位成本 × 持有成本率))

年需求量 = 日均需求 × 365
单位年持有成本 = 单价 × 持有成本率（默认0.25，即库存价值的25%）

年订货次数 = 年需求量 / EOQ
年订货成本 = 年订货次数 × 单次订货成本
年持有成本 = (EOQ / 2) × 单位年持有成本
年总成本 = 年订货成本 + 年持有成本
```

**例子1：SKU001 A4复印纸（中价商品）**

```
年需求量    = 30.5 × 365 = 11132.5件
持有成本    = 25 × 0.25 = 6.25元/年
EOQ        = √(2 × 11132.5 × 200 / 6.25)
           = √712480 = 844件

年订货次数  = 11132.5 / 844 = 13.2次
年总成本    = 13.2×200 + (844/2)×6.25 = 2640 + 2637.5 = 5277.5元

含义：每次补844件最经济，一年补13次
```

**例子2：SKU006 芯片X3-100（高价商品）**

```
年需求量   = 18 × 365 = 6570件
持有成本   = 120 × 0.25 = 30元/年
EOQ       = √(2 × 6570 × 200 / 30) = √87600 = 296件

年订货次数 = 6570 / 296 = 22.2次
总成本     = 22.2×200 + (296/2)×30 = 4440 + 4440 = 8880元

含义：单价高的商品，EOQ较小，少囤货多补货
```

**例子3：SKU008 电阻10K（低价商品）**

```
年需求量   = 120 × 365 = 43800件
持有成本   = 0.5 × 0.25 = 0.125元/年
EOQ       = √(2 × 43800 × 200 / 0.125) = √140160000 = 11839件

年订货次数 = 43800 / 11839 = 3.7次
总成本     = 3.7×200 + (11839/2)×0.125 = 740 + 739.9 = 1479.9元

含义：单价低的商品，EOQ很大，一次多囤少补
```

**三种价格商品的EOQ对比：**

| | 低价商品（电阻） | 中价商品（复印纸） | 高价商品（芯片） |
|---|---|---|---|
| 单价 | 0.5元 | 25元 | 120元 |
| EOQ | 11839件 | 844件 | 296件 |
| 年补货次数 | 3.7次 | 13.2次 | 22.2次 |
| 逻辑 | 多囤少补 | 中等 | 少囤多补 |

---

### 公式3：提前期需求

```
提前期需求 = 日均需求 × 采购提前期
```

**例子：SKU001**

```
提前期需求 = 30.5 × 7 = 214件

含义：从下单到到货这7天，仓库还要消耗214件，补货时必须考虑这个量
```

---

### 公式4：补货点（Reorder Point）

```
补货点 = 提前期需求 + 安全库存
```

**例子：SKU001**

```
补货点 = 214 + 200 = 414件（使用CSV里预设的安全库存200）

含义：当库存降到414件时必须下单，否则到货前库存会跌破安全库存
```

---

### 公式5：建议补货量

```
基础补货量 = 补货点 - 当前库存 + 提前期需求
建议补货量 = max(基础补货量, EOQ)
```

**例子：SKU001**

```
基础补货量 = 414 - 50 + 214 = 578件
EOQ       = 844件
建议补货量 = max(578, 844) = 844件

含义：基础需求578件能补到安全线，但844件更经济，取大的
```

---

### 公式6：紧迫度判断

```
库存/安全库存 比值：
  比值 ≤ 0.5  → 🔴 紧急，立即补
  比值 ≤ 1.0  → 🟠 较紧急，尽快补
  比值 ≤ 1.5  → 🟡 需关注
  比值 > 1.5  → 🟢 正常
```

**例子：**

| SKU | 当前库存 | 安全库存 | 比值 | 判断 | 可维持天数 |
|-----|---------|---------|------|------|-----------|
| SKU001 | 50 | 200 | 0.25 | 🔴紧急 | 50/30.5=1.6天 |
| SKU006 | 20 | 150 | 0.13 | 🔴紧急 | 20/18=1.1天 |
| SKU003 | 500 | 300 | 1.67 | 🟢正常 | 500/45=11.1天 |
| SKU004 | 120 | 100 | 1.20 | 🟡需关注 | 120/8=15天 |

---

### 公式7：可维持天数

```
可维持天数 = 当前库存 / 日均需求
```

---

### 完整计算流程（SKU001为例）

```
用户问："SKU001要补多少货"

第1步：紧迫度   → 50/200=0.25 ≤ 0.5 → 🔴紧急
第2步：提前期需求 → 30.5×7=214件
第3步：补货点   → 214+200=414件
第4步：可维持天数 → 50/30.5=1.6天（非常危险）
第5步：基础补货量 → 414-50+214=578件
第6步：EOQ    → √(2×11132.5×200/(25×0.25)) = 844件
第7步：建议补货量 → max(578, 844) = 844件
第8步：年成本   → 13.2次/年，总成本5278元

最终建议：🔴紧急！建议补货844件，下单后7天到货，当前库存仅够1.6天
```
